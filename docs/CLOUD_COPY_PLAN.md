# Cloud-copy destination planning

Status: source-only first slice for #86. The `internal/cloudcopy` package makes an inert destination plan; it does **not** run rclone, read an artifact, enroll an account, copy a file, or authorize egress.

`MakePlan` binds a trusted enrolled profile ID, explicit action ID, durable job identity and canonical artifact digest/size to the existing managed-export filename policy. It appends a full SHA-256 action tag so an explicit second delivery of the same job receives a different remote key. All output paths stay under the fixed `foliorelay/` key prefix and a generated `fr_<profile-id>` remote alias; callers never supply raw `remote:path` syntax. The MIME-derived extension is retained, and long stems are truncated on UTF-8 rune boundaries.

The package accepts only declared provider types (`google_drive`, `onedrive`, `icloud_drive`, `nextcloud`, `s3`) as a schema boundary. This is **not** a provider qualification verdict. The caller must still authenticate and authorize the actor and job, durably bind one ActionID to one exact plan/artifact/profile, resolve the profile to a protected rclone configuration, verify the canonical artifact bytes, and assign a single dispatch owner before any upload. A provider-specific adapter must prove no overwrite or unintended object mutation in a concurrent hostile destination. Generic rclone `copyto` and `rcat` can overwrite existing files; `sync` can delete remote files, so no transfer is admitted by this planner. Remote-side deletion never changes the canonical artifact or intake record.

Disposable falsification on the host's rclone **v1.67.0**, local backend, 2026-10-24: `copyto` with `--immutable --retries 1 --low-level-retries 1` returned 0 and replaced `original` with `replacement`; a second invocation with the flags before the command again returned 0 and replaced it with `third-content`. `rcat` with the same flags returned 0 and replaced it with `fourth-content`. The source and destination were synthetic files under one run-owned `/tmp/folio-rclone-immutable-*` fixture. This is a local-backend/version observation, not a verdict on any cloud backend. It proves the adapter cannot rely on this generic flag as its no-clobber control.

Independent current-release check: official rclone **v1.75.2** Linux amd64 archive SHA-256 `349ac8fba6ff65d6247043f1750cdcb518ec5d500ef91463a10d37c0ccdf3702` matched the publisher's `SHA256SUMS`. In an ephemeral container, the local backend again returned 0 and overwrote `original` with `replacement` via `copyto --immutable`; `rcat --immutable` returned 0 and overwrote it with `third`. This strengthens the local-backend finding but does not qualify any cloud backend. The exact archive was test input only, not a deployed or approved sender binary.
